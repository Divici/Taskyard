### Q6 — One gotcha each

- **WebView2 transparency**: Transparent windows on Windows regress across Tauri/WebView2 versions, reported symptoms include a solid black/dark-grey background instead of true transparency, and a "ghost titlebar" artifact appearing during window drag or focus change specifically with "transparent": true (reported against WebView2 144.0.3719.67 / Tauri 2.9.5). Treat window transparency on Windows as something to validate against the exact WebView2 runtime version in CI, not a fire-and-forget config flag. Source: https://github.com/tauri-apps/tauri/issues/14764 ; https://github.com/tauri-apps/wry/issues/692. Confidence: M
- **window-vibrancy acrylic**: Acrylic (apply_acrylic) visibly lags during window drag/resize on Windows 10 v1903+ and Windows 11 (build 22000+), a known limitation of the undocumented composition API it relies on, budget for this when the app is meant to feel "lightweight," since a Fences-like app's primary interaction (dragging/resizing named groups) is exactly the operation that triggers the lag. Source: https://github.com/tauri-apps/window-vibrancy/issues/47. Confidence: M
- **IPC payload size for icon bitmaps**: Returning binary data (e.g. base64-encoded PNG icon bitmaps) through a normal invoke command incurs real overhead, JSON doesn't support raw bytes, so Tauri serializes Vec<u8> as a JSON array (or callers base64-encode it), and both paths add CPU cost for decode on the frontend; one filed bug shows a large Vec<u8> image response taking unusually long to arrive in the frontend despite fast Rust-side processing. The documented lower-overhead alternative is Tauri's custom/asset protocol (a registered URI scheme served like an HTTP response) or an ipc::Response of owned bytes rather than JSON-wrapped strings, relevant directly to how Taskyard should ship per-icon bitmaps for hundreds of desktop items. Source: https://github.com/tauri-apps/tauri/issues/9654 ; https://github.com/tauri-apps/tauri/issues/7706. Confidence: M

### Q5 — One gotcha each

- **Finding (transparent windows on Windows):** `transparent: true` disables native Aero Snap window-snapping and disables system-menu/double-click maximize (maximize only works via Electron's own API call), requires DWM to be active (fails or degrades with DWM disabled), and is reported to cause resize flicker from DWM/Chromium-compositor desync. Click-through behavior (disableHardwareAcceleration plus setIgnoreMouseEvents) has also been reported to regress between Electron versions. · Source: https://github.com/electron/electron/issues/3155 , https://github.com/electron/electron/pull/28207 , https://github.com/electron/electron/issues/48064 · Confidence: M.
- **Finding (backgroundMaterial gotcha):** Setting backgroundMaterial: mica or acrylic alone only paints the material behind the non-client area (titlebar) by default — the client (content) area stays opaque/white unless the window is also set transparent: true (a documented community workaround: construct with transparent: true, show: false, then show() after content loads). Separately, multiple still-referenced issues report the material rendering solid black or losing rounded corners on maximize, with only a partial fix landed (PR #45456). · Source: https://github.com/electron/electron/issues/38454 , https://github.com/electron/electron/issues/38532 , https://github.com/electron/electron/issues/42393 , https://github.com/electron/electron/issues/46753 , https://github.com/electron/electron/pull/45456 · Confidence: M.
- **Finding (koffi + electron-builder packaging gotcha):** Same root cause as Q4 — koffi's native binary lives in a sibling @koromix/* package outside node_modules/koffi, so default/naive asarUnpack: ["node_modules/koffi/**"] configs silently fail to unpack the real native binary, causing an asar-can't-load-native-module runtime crash; both node_modules/koffi/** and node_modules/@koromix/** must be listed. · Source: https://github.com/renhaoyeh/electron-forge-plugin-koffi/blob/main/README.md · Confidence: M.

### Q2: Progman -> WorkerW -> SHELLDLL_DefView hierarchy and the 0x052C technique

- **Finding**: The desktop window hierarchy is Progman (top-level "Program Manager" window) which normally contains SHELLDLL_DefView (hosting SysListView32, the icon list) as a direct child; sending the undocumented message `0x052C` to Progman causes it to spawn a sibling `WorkerW` window behind the icon layer, which apps then locate via `EnumWindows` (find the WorkerW whose next sibling - not child - contains SHELLDLL_DefView) and use as a parent for custom background content. Source: https://www.codeproject.com/Articles/856020/Draw-Behind-Desktop-Icons-in-Windows-plus (community/primary reference article, not Microsoft-official). Confidence: M.
- **Finding**: "The desktop is not designed to have interactive children, so events regarding mouse movement, keyboard input, etc. will not reach your application" when a window is parented under WorkerW behind the icons - i.e., a WorkerW-parented child does not reliably receive mouse input while the real icon/Explorer layer sits on top of it in the same screen region. Source: same CodeProject article. Confidence: M. Gap: no source found (official or community) explicitly testing/confirming mouse-input delivery specifically when desktop icons are hidden (HideIcons=1) - not verified this pass.
- **Finding**: On Windows 11 24H2+, a real, reproducible regression exists: live-wallpaper apps (Lively Wallpaper) report the WorkerW window is not present immediately after startup / its handle cannot be located reliably, and wallpapers fail to render - the Lively maintainer states: "This is a Windows issue, as a workaround enable desktop icons." The bug correlates with desktop icons being hidden, and is intermittent (sometimes appearing only after some delay post-boot). Microsoft updates KB5050009 and KB5050094 are reported by users as having fixed/mitigated it in some cases. Source: https://github.com/rocksdanister/lively/discussions/2464, https://github.com/rocksdanister/lively/issues/2695, https://github.com/rocksdanister/lively/issues/2415. Confidence: M (GitHub maintainer/user reports; no Microsoft-official changelog entry found describing the underlying WorkerW/DefView parenting change itself - the root technical cause is not documented in any source found this pass, only its symptoms).

### Q3: Keeping a window at the bottom of z-order (non-parented) and Show-Desktop behavior
